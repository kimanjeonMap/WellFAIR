주사위 중간점검 파일 지도

myabweb에서 쓰던 방식(.do 주소, controller · dao · to 패키지, mapper-*.xml + SqlSession, WEB-INF/views/*.jsp)을 그대로 따르고, 그 사이에 service 한 칸만 추가했어요. 어떤 버튼을 눌렀을 때 어느 파일을 열어보면 되는지 바로 따라갈 수 있게, 화면마다 요청 하나가 거치는 파일을 한 줄로 늘어놓았습니다.

최종 시안을 보고 바뀐 것

처음 버전(예전 화면 시안 기준)에서 달라진 부분이에요.

  • 메뉴가 위쪽 탭으로왼쪽 세로 메뉴(sidebar.jspf)를 없애고, header.jspf 하나에 탭 4개(분석 지도 · 현장 확인 리스트 · 보관함 · 분석 리포트)를 넣었어요.
  • 취약요인 "개수"에서 "점수"로지하층 +30, 옥탑·위반 +20, 노후·침수 +15, 저지대 +5 같은 가중치 합계를 100점 만점으로 환산한 게 취약도 점수예요. 왼쪽 레이어 트리와 가중치 조정을 받는 AnalysisCriteriaTO, 상세 패널의 점수 구성 ScoreItemTO가 새로 생겼어요.
  • 지도 화면에 패널이 늘었어요분석 전에는 현장 확인됨 핀만 보이고, "분석 실행"을 누르면 점수 핀과 오른쪽 검색 결과 리스트(정렬, 페이지)가 떠요. 상세 패널에는 점수 구성, 건축물대장, 담당자 메모가 있어요.
  • 진행 상태 = 보관함 탭보관함의 신규 · 진행중 · 완료됨 탭이 메인의 진행해야 하는 · 진행중 · 진행완료 건수와 같은 기준이에요. 상태 컬럼을 따로 저장하지 않고 SQL에서 계산해서, 세 화면 숫자가 항상 같아요.
  • 현장 확인 리스트가 3화면으로목록(03, 펼치면 건물과 미니 지도), 수정(03-1, 보관함 건물 넣고 빼기), 상세 + 경로 지도(03-2). JSP 3개, JS 4개로 나눴어요.
  • 건물을 누르면 거주 가구도 (11/7 추가)오른쪽 패널을 "건물 정보 / 거주 가구" 탭으로 나눴어요. 같은 점수면 더 취약한 가구가 사는 건물이 우선순위가 높아요. 거주자 쪽은 파일 5개(ResidentTO, ResidentDAO, mapper-resident.xml, building-panel.jspf, resident-panel.js)에 모았어요. 데이터는 양천구 가구원 더미(1행 = 가구원 1명)라 "김영희 79세 · 심한 장애 · 차상위"처럼 사람 단위로 떠요.
  • 지도 API: 카카오 → 네이버 (11/7)다크 모드 때문에 네이버 지도로 바꿨어요. 파일 구조는 그대로이고, 지도를 직접 다루는 map-config·map-marker·map-main·field-map.js와 JSP의 SDK script 태그, app.properties 키만 바뀌어요. Java 쪽은 bbox(경도·위도 범위)만 받아서 영향이 없어요.
  • 대시보드 = 분석 리포트(06)요약 카드, 구·동별 취약 건물 막대, 요인별 정확도, LLM 요약이 있는 화면이에요. 메인의 건수 칩을 누르면 여기로 와서 상태별 건물 목록이 같이 보이게 했어요.

화면 하나에서 나가는 요청(가지)마다, 거치는 파일과 메서드 이름을 순서대로 적었어요. DAO 메서드 이름과 mapper id를 똑같이 맞춰서 검색 한 번으로 찾을 수 있어요. 오른쪽 회색 글씨는 피그마 프레임 번호예요.

유지보수를 위한 약속 7가지

myabweb에서 그대로 가져온 것과, 파일이 늘어나면서 꼭 바꿔야 하는 것을 함께 적었어요.

1. Controller는 DAO를 직접 부르지 않기

myabweb의 AbController는 AddrBookDAO를 바로 불렀는데, 여기서는 꼭 Service를 거쳐요. 그래야 "상태 건수"처럼 세 화면이 같이 쓰는 로직이 한 곳에만 있어요.

2. DAO는 자기 Service만 부르기

ArchiveDAO는 ArchiveService만 써요. 대시보드가 상태 건수가 필요하면 ArchiveService.getStatusCount()를 부르지, ArchiveDAO를 직접 잡지 않아요.

3. mapper id는 namespace까지 붙여 부르기

myabweb은 selectList("getList")처럼 id만 썼는데, mapper가 5개가 되면 같은 id가 생겨 오류가 나요.

session.selectList("mapper-field.getItemList", listId);

4. 이름은 4칸 모두 같은 단어로

Controller는 짧게, Service는 동사+대상, DAO 메서드와 mapper id는 완전히 같게.

MapRESTController.results() → MapService.getResultPage() → BuildingDAO.getResultList() → mapper-building.xml #getResultList

5. 진행 상태는 저장하지 않고 계산하기

보관함 건물(vulnerability_factor)이 현장 확인 리스트(survey_plan)에 없으면 TODO(신규), 담겼지만 조사 기록(survey_record)이 없으면 DOING(진행중), 기록이 있으면 DONE(완료). mapper-archive.xml의 <sql id="statusExpr"> 한 조각으로 계산하고, 라벨은 common/WorkStatus.java에만 적어요.

7. 거주자 데이터는 한 곳으로만 들어오기

거주자 테이블(household · person · residency · arrears) 컬럼을 읽는 곳은 mapper-resident.xml뿐이에요. 개인 우선순위 가점은 <sql id="priorityExpr"> 한 조각(고위험고립, 75세 이상, 심한 장애, 차상위·기초연금, 건보료 체납, 독박돌봄, 지하·옥탑층)이고, 건물 우선순위 정렬도 이걸 include해요. 컬럼이 또 바뀌면 이 mapper, ResidentTO, resident-panel.js 세 파일만 고치면 돼요. person.mbr_id는 로그인 회원(MemberTO)과 헷갈리니 TO에서는 residentId로 받아요.

6. 점수 계산 SQL도 한 군데서만

mapper-building.xml의 <sql id="scoreExpr">가 기준값·가중치로 점수를 만들어요. 도넛·핀·결과 리스트·상세, 그리고 대시보드(<include refid="mapper-building.scoreExpr"/>)까지 이 조각 하나를 같이 써요.

클래스·mapper 이름은 화면 기준(Member, Archive, Field, Resident) 그대로 두고 안의 SQL만 위 테이블을 써요. 더미 ID는 구마다 1부터라 적재 때 구로 +1,000,000 / 양천 +2,000,000 / 영등포 +3,000,000을 더했어요. 진행 상태는 vulnerability_factor · survey_plan · survey_record를 JOIN해서 계산하고, 현장 확인 리스트의 "완료됨" 탭은 "리스트의 모든 건물에 survey_record가 있으면 완료"로 계산해요. 고시원 요인은 sp_type = '고시원', 저가는 price_pct, 옥탑은 residency.res_flr = '옥탑층' 가구가 있는 건물로 계산해요. 에너지 급감은 뺐어요.
